# 组合交易记录设计

## 1. 问题与目标

持仓数量变化目前只覆盖最新状态，无法回答何时买卖、由哪个入口触发、属于哪个组合，也无法在个股 K 线上复盘卖出后的走势。本次把已有 `journal_trade` 从“人工成交日记”扩展为用户级统一交易流水，保留已有日终人工录入，同时覆盖组合、真实持仓镜像和微信 Bot 变动。

成功标准：数量变化只生成一次正确方向的流水；记录严格按当前用户隔离；无真实成交价时明确显示估算；个股日/周/月 K 线可见 B/S 点；卖出记录可查看最新涨跌、卖后最大上涨和最大下跌。

## 2. 方案比较

### 方案 A：新建组合交易表

- 优点：模型完全独立，历史字段整洁。
- 缺点：与 `journal_trade` 形成两套真实成交记录，页面和 K 线需要合并，用户难以理解。

### 方案 B：直接复用 Smart Trader 的 `trade_event`

- 优点：已有成交字段和幂等键。
- 缺点：该表属于外部交易者证据确认链路，不是登录用户资产，权限和业务语义不匹配。

### 方案 C：扩展 `journal_trade`（采用）

- 优点：统一人工成交与持仓变动，迁移成本低；原接口兼容；能复用已有用户隔离。
- 缺点：历史人工记录没有组合和变动前后数量，需要允许这些字段为空。

## 3. 数据模型

在 `journal_trade` 增加证券名称、组合快照、归属人、变动类型、变动前后数量、精确时间、来源、来源引用、价格来源和估算标记。`user_id` 始终来自登录上下文，不能由请求传入。

方向由数量差计算：`0 -> 正数` 为 `BUY/OPEN`，增加为 `BUY/ADD`，减少但仍持有为 `SELL/REDUCE`，`正数 -> 0` 为 `SELL/CLEAR`。只有数量发生变化才写流水，成本、止损、备注等编辑不生成交易。

Bot 使用 `requestId + code` 作为来源引用，并建立用户、来源、引用、代码唯一索引。相同请求重试或第一次已经成功后再次执行，不会重复写流水。

## 4. 价格口径

组合编辑和 Bot 输入可选真实成交价、成交时间。提供且大于零时记录为用户或 Bot 报告价，`estimated=false`。未提供时使用 `stock_basic.latest_price`；若仍不可用则使用交易日最近收盘价；都不可用时价格为空。后三种情况均标记 `estimated=true`，页面显示“估算”，不把持仓平均成本冒充成交价。

卖后表现以记录价格为基准：最新涨跌使用最新行情；最大上涨和最大下跌只统计成交日之后的日线，避免把卖出前的当日高低点算入“卖后”。没有有效基准价或后续行情时返回空值。

## 5. 写入链路

`PortfolioServiceImpl` 是统一写入点。Web 保存/删除、文本导入、`my_holding` 镜像都在持仓落库的同一事务内写交易流水。微信 `HOLDING_IMPORT` 从“全删全建”改为按代码比对：仅删除缺失项、更新数量或成本变化项、新增新项，未变化的持仓保持不动。

流水写入失败应回滚对应持仓变动。行情快照和卖后指标查询失败不改变历史流水，只让派生指标为空。

## 6. API 与界面

- `GET /api/trades`：按组合、代码、方向、来源分页查询当前用户交易。
- `GET /api/trades/markers?code=...`：查询当前用户某股票的 K 线标记。
- `/trades`：从组合页进入的交易记录工作区，提供筛选、来源/估算状态和卖后表现。
- 个股页：在主 K 线叠加 B/S 点；标签优先显示归属人，其次显示组合名；同日同方向多条记录合并显示并在提示中展开。

交易查询单独调用，不写入 `StockDetailResp`，避免私人数据进入股票详情的共享缓存边界。

## 7. 风险与边界

- 上线前已有的持仓只能表示当前状态，无法可靠重建历史交易，本次只记录功能上线后的新变化。
- 历史 `journal_trade` 保持可读，组合、来源和前后数量为空时按“人工录入”展示。
- 组合删除后仍保留交易中的组合名和归属人快照，保证审计记录不丢失。
- 当前没有分钟级历史行情，卖后最大涨跌按后续日线计算；成交当日只用实时最新价计算最新涨跌。
